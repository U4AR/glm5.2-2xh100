Latency & overlap profile · GLM-5.2 hybrid MoE decode

Where a token's time goes — and how the GPU and CPU actually share the work

GLM-5.2 keeps 96 of 256 experts on the GPU and computes the rest on the CPU, concurrently. Per MoE layer the CPU job is fired async, the GPU experts run in parallel, then the layer waits for whichever lane is slower. The question isn't just "how long is each stage" — it's who is waiting for whom. Measured below, in both the instrumented (eager) path and the production CUDA-graph path.

What's the bottleneck now

There are two honest answers, at two levels. One is fixed and dominates the clock; the other is the only thing the expert-placement work can move.

Biggest absolute cost · fixed

Attention + dense base  35.5 ms

~71% of a fast decode step is memory-bandwidth-bound: reading the attention (MLA) and dense/shared weights plus the KV cache from HBM, every single token. It's there even with zero experts on the CPU. Nothing in expert placement touches it — only MTP / speculative decode amortizes it across accepted tokens.

Biggest controllable cost · the pole

CPU expert compute  ~3 ms / expert

Inside the MoE region the CPU is the exposed pole in production: the GPU finishes its resident experts in a fraction of the time and then idles waiting for the CPU. Each genuine expert that isn't GPU-resident adds ~3 ms/token. The GPU is under-utilized during decode; CPU expert throughput is the wall.

How CPU and GPU overlap — per MoE layer

Two lanes, drawn to real timing. The GPU / main-stream lane runs submit → mask → the resident-expert GEMM → a wait → merge. The CPU worker lane runs the non-resident experts, kicked off by submit and running in parallel. Whether the CPU is hidden depends entirely on whether it finishes inside the GPU's window — and that window is ~4× narrower in production.

Now CPU 0.20 ms > GPU 0.09 ms: the GPU sits idle ~0.11 ms/layer waiting. Summed over 75 layers this is the ~3 ms/token per expert you pay on the wall clock.

The overlap machinery is real and it works — the CPU genuinely computes its experts while the GPU computes its own. The catch is a speed mismatch: CUDA graphs make the GPU MoE ~4× faster but do nothing for the CPU's AVX kernels, so at production speed the tiny GPU window can no longer hide the CPU, and the GPU ends up waiting.

What this says

  • The GPU is not the bottleneck during decode — it's underused. Per layer it finishes its experts in ~0.09 ms and then waits ~0.11 ms for the CPU. The overlap works; the two lanes are just mismatched in speed.
  • CPU expert throughput is the pole we can move. Each non-resident genuine expert = ~3 ms/token of GPU idle-wait. Fewer CPU experts (substitution) or a faster CPU kernel shortens that lane directly.
  • Placement can't win it. At 96/256 the per-layer top-2 set outgrows the resident slots on diverse tokens, so some genuine top-2 always lands on the CPU — the accuracy-safe 44→50 ms gap.
  • The real lever is MTP / speculative decode. It's the one thing that attacks both poles at once: it amortizes the fixed 35.5 ms base and the per-token CPU wait across several accepted tokens — without dropping any expert.
