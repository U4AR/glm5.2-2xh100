Anatomy of one forward step

Each step runs the CPU experts asynchronously while the GPU works, so a layer costs max(cpu, gpu). The GPU finishes its share in 37 ms and then waits: for 80% of every step the accelerators are idle behind 6.1 expert GEMMs per layer running out of host DRAM.

The interesting part is what is not saturated. The CPU holds 94% of its cores busy while retiring 2.0% of its int8 throughput and pulling 38% of its memory bandwidth. So the expert path is limited by neither arithmetic nor DRAM throughput: what is left is per-layer submit/sync serialisation and memory latency — 75 round trips per forward pass, each too small to hide its own overhead. Meanwhile the two H100s sit at ~20% kernel duty and ~4% of HBM bandwidth, and the SSDs are untouched.

How each number was obtained

  • Time per token — a streaming completion, timestamped per SSE chunk. One chunk is one forward step, and MTP emits 3.05 tokens per step, so token time is the step time divided by the server's own token count, not the chunk rate.
  • GPU compute and stage split — the server's /start_profile endpoint (torch profiler, CUPTI). Busy time is the union of kernel intervals, so concurrent kernels are not double-counted.
  • GPU bandwidth — NVML memory duty cycle, cross-checked against an analytic bytes-per-token model of the weights actually read. Both land at ~4%.
  • CPU occupancy — /proc/stat deltas over the decode window only, prefill excluded.
  • DRAM ceiling — a STREAM triad and a pure-read kernel built and run on this box while the server was idle. The triad is counted at 32 B/element, not 24, because the store pulls the line in first.
  • DRAM demand — analytic: 6.12 CPU-resident experts x 19.5 MB x 75 MoE layers per token. This assumes uniform routing across the 60 GPU-resident experts; hotcore placement biases the hot experts onto the GPU, so treat it as an upper bound. The contention probe is the assumption-free cross-check.
  • SSD — /proc/diskstats plus major-fault and swap counters.
  • Not used: hardware DRAM counters. This VM exposes no uncore/UMC PMU and perf_event_paranoid is 4, so bandwidth is bracketed by the two methods above rather than counted directly.

Reproduce

MODEL=GLM5.2 .venv/bin/python bench/profile_occupancy.py \
    --tokens 400 --torch-tokens 150
.venv/bin/python bench/profile_report.py bench/profile_out/results.json

Runs against a live server and does not restart it. It does briefly drive the torch profiler and a 4-thread memory probe, which slow decode while they run.
