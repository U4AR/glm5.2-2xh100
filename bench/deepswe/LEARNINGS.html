The one that matters most

run_server_int4.sh defaults SLEEP_ON_IDLE=1. An agent pauses for seconds between calls while it runs shell commands, so the server goes idle, releases KV memory, and flushes the prefix cache on every single step. Each step then re-prefills the entire conversation from scratch on the CPU expert path.

#cached-tokenPaceSteps in 12 min
SLEEP_ON_IDLE=10, always100 s/step~7
SLEEP_ON_IDLE=016k → 62k, rising9 s/step86

It costs nothing on single-shot decode benchmarks — which is every benchmark in this repo — which is exactly why it survived as a default. It is harmful for anything multi-turn: agents, chat, coding harnesses.

The failure ledger

Ordered by attempt, because the order carries the lesson: each fix exposed the next constraint, and three of them were caused by tuning one dimension without checking what it cost elsewhere.

01
died at step 11 · MEM_FRACTION=0.95

TP1 OOM'd creating the MTP draft at boot with 43 MiB free. The supervisor took the SIGQUIT and died; the two schedulers survived orphaned and served for an hour before going down mid-task. /health returned 200 throughout.

02
died at step ~15, all three agents · concurrency vs VRAM

The MTP draft's triton forward_extend needs ~542 MiB per concurrent prefill. Three agents, 472 MiB free, four OOMs. The concurrency was added to meet a time budget, against headroom never checked.

03
refused to boot · MEM_FRACTION=0.88

0.88 is below the weight floor (~0.90). Lowering mem-fraction is not the lever for headroom — GPU_EXPERTS is, at roughly 0.40 GB per expert.

04
4 steps in 32 minutes · max_running_requests=2

Three agents plus litellm retries produced #queue-req: 5 against two slots. An abandoned client request is not aborted server-side, so every timeout left a zombie holding a slot and triggered more retries.

05
stalled indefinitely · --sleep-on-idle

The prefix cache flush described above. #cached-token: 0 for hours while health, VRAM, scheduler count and queue depth were all green.

06
died at step 82 · GPU prefill + 98k KV pool

Two changes made at once. As context reached 63k the pool filled, VRAM climbed to 94.8 of 95.8 GB, and the ~5 GB GPU prefill workspace no longer fit.

07
died at step 142 · ContextWindowExceededError

81,994 tokens against an 81,920 limit. Server entirely healthy — no OOM, no restart. The only failure of the seven that wasn't a resource misconfiguration.

Rules to carry forward

Green health checks prove nothing

Failures 01, 04, 05 and 07 all ran with health=200, both schedulers alive, and VRAM resident. A half-crashed server answers health checks perfectly well, and a starved or cache-flushed one answers them fast.

Watch throughput signals, not liveness signals:
#cached-token (must be non-zero and rising) · #queue-req (must stay ~0) · OOM count in the server log (must not rise)

Concurrency has three independent prices

Each agent needs VRAM headroom for its prefill workspace, a request slot, and enough KV pool to keep its own prefix cached. Paying one and not the others produced failures 02, 04 and 06 in sequence — the same mistake three times, in three different currencies.

Before raising concurrency, budget all three: prefill VRAM ×N, MAX_RUNNING ≥ N + retries, pool ≥ N × peak context × 1.3

Change one dimension per boot

Failure 06 enabled GPU prefill and a larger KV pool together; each was fine alone and fatal together. A boot costs about four minutes. Diagnosing a coupled failure costs an hour.

One variable per boot, and record the free-VRAM figure at idle each time

A watchdog's restart config must match the launch config

The watchdog carried a hardcoded MEM_FRACTION=0.88 from an earlier experiment. When it correctly detected a dead server, it "recovered" it into a boot loop that could not start at all.

Derive the watchdog's restart command from the same source as the launch, or assert on boot that they match

An errored trial is not a failed trial

The first version of report.py scored every crashed run as fail and printed a tidy "0/3" table for three runs that never reached the verifier. That table would have read as a catastrophic quality result for the top-2 tier.

Only a verifier reward is a verdict. Absent reward → ERROR, excluded from the denominator, cause printed.

The one real signal so far

Run 07 reached 142 steps and 81,201 tokens of context on ts-pattern-match-each without submitting. Datacurve's graded GLM-5.2 runs solve that task in a median of 48 steps / 61,110 tokens.

Roughly 3× the steps for the same task is what expert-substitution degradation would look like. It is a hypothesis, not a finding: one rollout, no top-8 control on this box, and a truncated run cannot be distinguished from a slow-but-correct one. It becomes evidence only if top-8 finishes the same task in ~50 steps on the same server — which is the first thing worth running tomorrow.

Host changes made today

  • Rootless Docker host access — ~/.config/systemd/user/docker.service.d/host-loopback.conf removes --disable-host-loopback, without which no container can reach the server at all. The host is 10.0.2.2 from inside a container, not the LAN IP. This weakens container isolation host-wide; delete the file and restart docker to revert.
  • Docker data-root moved to /data/docker-bel; the root disk was 93% full and each task image is 2.7 GB. A stale 23 GB copy remains at ~/.local/share/docker/overlay2 and is safe to delete.
  • Pier egress proxy — patched agent_setup.py so squid's Safe_ports includes 8000; it allowed only 80 and 443.
  • Cgroups — no CPU delegation on this host, so Pier needs --cpus ignore --memory ignore or containers never start.
